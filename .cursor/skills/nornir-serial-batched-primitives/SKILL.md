# Serial + batched primitives

Paired rule: [`.cursor/rules/Serial-batched-primitives.mdc`](../../rules/Serial-batched-primitives.mdc).

## Before merge

1. **Grep callers** of any changed primitive (serial and batched entry points).
2. **Keep serial/batched mirrors aligned** — same gates, tolerances, and semantics unless an intentional divergence is documented in this skill.
3. **Run the verification matrix** below for affected pathways.
4. **Final performance sign-off** must use a **real section with ≥100 tiles** (default: RPC3 0195 per `.vscode/launch.json`), with downsample and refine parameters matching launch configs — **not** the grid refine input section fixture (4 tiles).

| The batched centroid window must **wrap**, but the centroid must **not** be re-wrapped | `batched_find_peak` refines the argmax over a `(2r+1)` window. | The batched-FFT chunk optimum is a **working-set size in bytes**, not a cell count, so "fill the batch to whatever fits" maximises the wrong quantity | Sweeping chunk size at fixed total work across three cell sizes on an RTX 4500 Ada (float32, median of 7, results identical at every chunk) puts the best chunk at **1024** cells of 64px (0.0353s, worst 0.3001s, **8.50x** spread), **256** of 128px (0.1250s, spread 2.32x), and **64** of 256px (0.1326s, spread 1.97x). | `ScoreOneAngle` is **stochastic**, so any search built on comparing two of its weights is a random walk | The padding fill and the rotation-corner fill both draw from the shared generator, so scoring one scale twice returns different weights: noise sd **9.3e-02** against a mean near 1.9 on a real pair at angle 30, an **11–17% relative spread**. | An FFT frame should be the nearest **even 5-smooth** size, not the nearest power of two — and odd frames carry a half-pixel offset bias | `_fixed_correlation_shape` rounded the brute sweep's frame up with `NearestPowerOfTwoWithOverlap`, so the ds32 pair's 6000px requirement became **8192** — 1.86x the area for nothing (filed as #234, option 1). Both pocketfft and cuFFT are fast at any 5-smooth size, and since powers of two *are* 5-smooth the rounded result can only ever shrink, so frame memory cannot regress. Measured across eleven required sizes from 4100 to 8000 on float32 `fft2`: **1.21x–4.62x on numpy, 1.06x–2.95x on CuPy**, with one exception worth knowing — a requirement near 7300 picks 7500, which is **5.7% slower than 8192 on CuPy** while still 1.39x faster on numpy. Power-of-two frames are always even, which is the only reason this never surfaced; it *is* reachable today via `pad_image_for_phase_correlation(power_of_two=False)`, which rounds with `DimensionWithOverlap` and can return an odd size (two assessment scripts use it — filed as #238). General rule: a padded FFT frame has two independent requirements — *large enough* to hold the rotated content and the unambiguous offset range, and *cheap to transform*. Rounding to a power of two conflates them and always overshoots the first; and whenever you change frame sizing, check the centring convention, because a size rule that admits odd sizes silently changes what "zero shift" means. Pinned by `tests/test_smooth_fft_frame_size.py`; #234 remains open for the 11x angle×scale cross product, whose cheap fix routes through `_refine_scale_local` — the ternary search #95 measured as a random walk, so it is blocked on #95 rather than merely unimplemented |
| A memory *reserve* running out must not also destroy throughput — and clamp the **budget**, not the special case | `batched_fft_cell_chunk_size` subtracted a 512 MiB headroom reserve from 40% of free VRAM, and returned a chunk of **1** when that went negative, i.e. below 1.28 GiB free — one CUDA launch per cell (#236). First, **returning 1 is only correct if one cell genuinely will not fit, which is a different question from the reserve being exhausted** — the reserve exists to protect *other* allocations, so losing it should cost you the reserve, not the batching; the fallback still respects the same 40%-of-free bound, so it can never claim more than the ordinary path. The weight *curves* correlate with full resolution only **+0.74 to +0.83**, because off the peak the objective is the #95 noise floor (sd 9.3e-02 on a mean near 1.9) — so the coarse ordering *below rank 1* carries no information and a top-K refine is mandatory; do not narrow to K=1 on the strength of these ranks. And what makes rank 1 reliable is the peak's **margin** over that floor (2.77 vs 2.11 at full resolution, widening as resolution drops), so any pair with a flat objective — exactly the `_LogPolar` case in #235 — will not benefit and must fall back. General rule: when an expensive exhaustive search is the accuracy baseline, price *evaluating it cheaply* before pricing *shrinking it*; the second changes what is searched and needs an accuracy argument, the first only needs the ranking to survive. Characterization pinned in `tests/test_brute_decimated_ranking.py` (5 fast tests ~10s; 2 `slow` re-derive the full-resolution comparison).
